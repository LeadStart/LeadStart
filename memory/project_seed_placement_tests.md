**The 2026-08-20 health-score "drop" was the scoring model, not deliverability.** All five mailboxes went 100 → 95/85 in one step at 2026-08-20 01:30 UTC, the moment commit `7538c9a` deployed: −5 everywhere for DMARC `p=none` (new grading) and −10 on molly/jessica/christy for **0 replies across 134 sends in 14 days** (new reply signal). Emily sits at 95 only because she has replies — and as of 2026-08-22 there were just **3 native-email replies in 30 days in the whole org, all on emily**, across ~540 sends (~0.5%). The zero-reply warning is real data, not a bug; it's exactly the ambiguity seed placement resolves.

**What shipped 2026-08-22 (committed to master; `00068` apply + push/deploy pending — the Supabase dashboard session had expired, so the migration could not be applied from the session):** `seed_inboxes` / `placement_tests` / `placement_test_results` + `organizations.placement_test_interval_days` (default 7). A placement test sends one probe from a sending mailbox to every active seed on a *different* domain, then reads each seed via the existing DWD `gmail.readonly` scope (`rfc822msgid:` search with spam included) for the folder (INBOX / CATEGORY_PROMOTIONS / SPAM) and the receiver's `Authentication-Results` SPF/DKIM/DMARC verdicts. Two probe modes: **neutral** (short link-free note → reputation + auth) and **campaign copy** (step 1 rendered with sample tokens → the real copy). Neutral lands but campaign doesn't → copy problem; both spam → domain/mailbox reputation; receiver auth fails → DNS/DKIM problem. Pure logic in `src/lib/deliverability/placement.ts`, I/O in `placement-runner.ts`, cron `run-placement-tests` (every 10 min: finalize + weekly auto-probe), health component `seed_placement` (spam ≥50% −45 / any spam −25 / any missing −10 / Promotions majority −5; >7 days old = unchecked).

**Why:** every other health signal is a proxy (DNS config, blacklist, bounces, zero-reply). Daniel asked for "a better metric as to WHY" scores dip; the receiver-side auth verdict + folder is that metric. The sending mailboxes themselves double as seeds across the three client domains (zero new setup) — same-domain pairs are skipped because same-tenant delivery is never filtered.

**How to apply:** Probe sends are deliberately NOT written to `native_sends` (they must not move the ramp, daily cap, bounce rate, or reply denominator) and seeds are never mutated (no `gmail.modify`; this is measurement, not a warmup game — see [[project_no_warmup_pool_deliberate]]). Don't turn a small panel into an auto-pause gate on its own; critical needs corroboration. Test sends (the Send button) now go to a chosen recipient (default: login email) with the same neutral probe — self-sends are refused because they prove nothing. Workspace-only seeds for now; M365/Yahoo would need Graph/IMAP readers (`seed_inboxes.provider` reserves room).
