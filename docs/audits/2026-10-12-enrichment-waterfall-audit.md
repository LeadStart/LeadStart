# Email-enrichment waterfall audit (read-only, 2026-10-12)

**Question.** The waterfall exists to find every relevant business and its decision-maker's email as cheaply as possible. Where do leads dead-end, and what would recover them?

**Scope and citations.** The audited checkout is the worktree `saasassins-campaign-objectives-394fc7` at `7ac5940`. `master` (`db085c1`, the code that auto-deploys) is 7 commits ahead on exactly these files (`c5c4003` pool release, `9fa8465` Layer 1 pages, `94d7dcf` **company-inbox fallback**, `e2d3834` profile title / own company page / other-employer emails, `de633d2` Layer 2 on Claude Haiku 5.5, plus two UI commits). Two more sibling worktrees hold related, not-yet-merged work: branch `6234762` (`intelligent-dhawan`) = pattern_mv guess order + paid-guess limit; worktree `modest-curie` (uncommitted) = per-provider cost breakdown + Perplexity request fee. Citations are `file:line` in the worktree unless marked **(master)** (line numbers in `master@db085c1`) or **(branch 6234762)**. Nothing was modified; no paid API was called.

**Measured basis.** (a) The owner's numbers for the national LinkedIn import (3,234 people): 529 verified + 231 catch-all owner emails (23%), 213 company-inbox-only, 2,127 with no LinkedIn company page of which 1,040 got no website, 440 people x 6 invalid guesses, 227 domains with no MX. (b) A read-only SELECT probe I ran against production (PostgREST, service role read in-process from the main checkout's `.env.local`, nothing printed) over the **17 enrichment runs created since 2026-10-11** (3,685 items, 3,429 with a LinkedIn URL, 3,032 distinct LinkedIn contacts; includes the 2026-10-11 test runs and one run still in flight, so totals differ slightly from (a)). Probe script: `scratchpad/probe-items.mjs`, output `scratchpad/probe-output.txt`. Everything labelled *estimate* is mine.

## 3. The pattern guesser

**As audited (worktree = master).** Candidates, in order: `first.last@`, `first@`, `flast@`, `f.last@`, `last@`, `firstlast@` (`pattern-mv.ts:37-66`). Loop (`:133-159`): first `ok` wins (conf 85); `catch_all` remembers the first and **continues through all remaining candidates** (`:150-153`); `unknown`/`error` continue and mark the item indeterminate (`:154-157`); `invalid`/`disposable` continue (`:158`); tick deadline mid-item -> inconclusive (`:134-136`). After the loop: catch-all accepted only with `acceptCatchAll` (conf 40, `:161-163`), else inconclusive (`:164-172`) or not_found (`:173-179`). Charging: one credit per `ok`/`invalid`/`disposable` (`:68-72`), catch-all/unknown free; the cron books `credits x $0.0037` (**master** `route.ts:953, 1094-1098`; `pricing.ts:27`). Cron limits: batch 25, concurrency 5, MV timeout 6 s, 40 s deadline (**master** `route.ts:100-103`). Worst case 6 credits = $0.022; the no-MX guard (`:871-875`) is the only pre-check.

**Measured (probe + branch 6234762's replay).** Finds by winning position on this import: pos 1 `first.last@` 125, pos 2 `first@` 155, pos 3 `flast@` 47, pos 4-6 **12 of 340 (3.5%)**. Misses: 455 items at 6 credits (2,730 credits ~ $10.10), 23 at 4, 15 at 5. The branch's replay over all 635 confirmed finds (32 runs): `first@` 407, `flast@` 141, `first.last@` 51, `firstlast@` 16, `last@` 12, `f.last@` 8; the 4th guess costs ~52 credits (~$0.19) per extra find.

**Already built on branch 6234762 (not merged):** new order `first@ -> flast@ -> first.last@ -> firstlast@ -> last@ -> f.last@` (`email-patterns.ts:25-59`), an org setting `pattern_max_credits` (default 3, 1-6; `types/app.ts`, `auth.ts`) enforced at `pattern-mv.ts:100-103`, capped misses final (no retry, `:134-145`), banner count. Its replay: national import 142 -> 130 finds for -46% credits (3,203 -> 1,725); all runs 635 -> 599 for -44%. Probe shows two items already carrying its note (`paid-guess limit 3`), so a dev server on that branch has run the cron against production.

**Cheaper policy, on top of that branch (my additions):**
1. **Early stop on the first `catch_all`.** It is a domain property; the remaining calls are free but cost up to 5 x (1-6 s) of a 40 s tick and push items into "deadline" inconclusives. Zero credits saved, fewer D6. Trivial.
2. **Domain-level negative cache within a batch/run.** 137 of the 440 all-invalid people sit on 38 shared domains, mostly franchisors (`jan-pro.com` 17, `janiking.com` 14, branch doc). Once one person on a domain comes back all-invalid at the cap, skip the next people on that domain in the run (or cap them at 1). *Estimate:* ~100 x 3 = 300 credits (~$1.1) saved per 3,000 people, ~0 finds lost (franchise unit owners do not have mailboxes on the franchisor domain). Small: group `mvItems` by domain in `runPatternMvBatch`.
3. **Positive same-domain prior.** If another contact on the domain already has a `pattern_mv` or `harvestapi` email, derive its pattern and try it first (two co-owners are common). Small; saves 1-2 credits on the second person and finds the pos-4-6 cases the cap would drop.
4. **Published-format inference and the free-mail skip** (section 2). The branch measured the skip on Scrap.io law firms: 5 of 20 firms publishing only free-mail still verified on their own domain, so **cap at 1 rather than skip**. Only applies where a crawl exists (Maps/Scrap.io, or LinkedIn leads in a scrape band).
5. **D6: a longer MV timeout on the retry.** 157 items (4.6%) ended with every answer `unknown` at 6 s; MV accepts up to 60 s and `unknown` is free. Use 20 s on `attempts >= 1` (the deadline already parks leftovers for the next tick). *Estimate:* 30-50% resolve -> +14-23 finds per 1,000 LinkedIn leads for ~1-3 credits each.
6. **Route capped/all-invalid misses to a pay-per-hit finder** (section 4) instead of the 4th-6th guess: $0.049 per hit vs ~$0.19 per extra find from guessing.

**Trade-off query (enrichment_run_items).** Credits per item can be derived only for pattern_mv items whose last phase write was the waterfall: `cost_usd` is **overwritten per phase** (set, not added: domains **master** `:1268`, naming `:1582`, waterfall `:943/:1017`, scrape miss `:2446`), and the no-MX skip (`:875`) writes no cost, leaving the domains-phase value (the probe's 297 "1-credit" misses are mostly these). So:
```sql
-- a) credits burned per outcome (pattern_mv only, excluding the no-MX skip)
select waterfall_status, round(cost_usd / 0.0037) as credits, count(*)
from enrichment_run_items
where run_id in (<runs>) and waterfall_method = 'pattern_mv'
  and waterfall_status in ('found','not_found')
  and coalesce(waterfall_notes,'') not like 'domain has no mail server%'
group by 1, 2 order by 1, 2;
-- b) winning position of each confirmed find (strip non [a-z0-9] from the names first)
select case split_part(email,'@',1)
         when f||'.'||l then 1 when f then 2 when left(f,1)||l then 3
         when left(f,1)||'.'||l then 4 when l then 5 when f||l then 6 else 0 end as pos,
       verification_result, count(*)
from (select *, regexp_replace(lower(first_name),'[^a-z0-9]','','g') f,
                regexp_replace(lower(last_name),'[^a-z0-9]','','g') l
      from enrichment_run_items where run_id in (<runs>)
        and email_provider = 'pattern_mv' and waterfall_status = 'found') x
group by 1, 2 order by 1, 2;
```
Credits saved by a cap of N = sum over misses of `max(0, credits - N)` + over finds at position > N of the credits past N; finds lost = finds at position > N. (The probe's node version of this is in `probe-items.mjs`.)

**Exact write path (master `94d7dcf`).** Scope on the run snapshot `waterfall_config.company_inbox_fallback` = `"opted_in"` (enqueue, when any contact's `addons.company_inbox_fallback` is true; **master** `enqueue-enrichment.ts:256-284`) or `"all"` (Contacts -> Enrich with the box ticked, **master** `enrich/start/route.ts:96-97, 350`). Routing: an opted-in named item in a `pattern_mv` band becomes `scrape_plus_pattern` so an inbox is captured (`waterfall-routing.ts:41` **master**, applied in `seedWaterfallItems` `:1842-1878`). Promotion: `applyCompanyInboxFallback` (**master** `:1960-2013`) runs when the waterfall has nothing pending, before activity/verify seed (`advancePhase` `:3053`): candidates = items `waterfall_status in (not_found, error)` with `email` null, contacts with `email` null and `company_email` set; `promoteCompanyInbox` (`:2015-2066`) writes `contacts.email` **fill-only** (`.is("email", null)`, `:2031`) with `enrichment.email = {provider: site_scrape, kind: company_generic, confidence: 30, via: company_inbox_fallback}` (`company-inbox.ts:23-36`), tags `enriched`+`site_scrape`, item `found` / `email_provider site_scrape` / confidence 30 with the miss reason kept in the note; a 23505 (inbox already another contact's email) leaves the item `skipped`. Name-less leads keep the older backfill (`finishWaterfallMiss`, `:2414-2446`) with the same provenance helper. Test: `scripts/test-company-inbox-fallback.ts`.

**Downstream checks - all consistent:**
- **Tier classifier**: `kind = company_generic` -> `company` (`email-tier.ts:39`); every caller passes `email_kind` (contacts page `:354` via `Contact.email_kind` `types/app.ts:528`; LinkedIn panel `:1393, 1437, 2898`; Maps panel `:462`; enrich run route `:81-95`).
- **Outcome ledger**: `company_email`, not `personal_email`; `bestTier = tier_company` (`outcomes.ts:74-87`). Billing tiers stay right.
- **TuBe handoff**: `tubeEmailStatus` needs tier `person` + MV ok, and its published branch excludes `company_generic` (`handoff.ts:248-262`) -> skip `email_not_verified` (`:357-361`). Correct: TuBe only wants owners.
- **Send gate**: `run-native-sequences` mails `contacts.email` (`:830`) after `gateContactVerification` (`:846-861`); MV's `role` flag is stored only, never a decision (`policy.ts:15-16`), so an `ok`/`catch_all` inbox **is sent to**, with the campaign's `{{first_name}}` addressed to the owner. No enrollment path filters on tier (grep: no `company_generic` consumer under `src/lib/campaigns`, `src/lib/native`, `src/app/api/admin/campaigns`). Acceptable for owner-run firms, but it should be a per-campaign choice: add an `allow_company_inbox` check in the enroll/candidate routes, or at least surface the tier in the picker.
- **Verify phase**: the item now has an email, so `seedVerifyItems` (`:3091`) gives it its first MV verdict (1 credit if ok/invalid), as documented.

**Three things to watch:**
1. **No-MX domains.** The promotion does not read the mail-host stamp. `company_email` is always on the firm's domain (the actor keeps only on-site role addresses, `extract.ts:155-159`), so for a D2 firm the promoted inbox is undeliverable: the verify phase will charge a credit to say `invalid`, and the contact sits with a dead `email`. Gate promotion on `readMailHost(...) !== "none"` (free; requires stamping LinkedIn leads, section 1a) or fall back to a published free-mail inbox.
2. **The fill-only contract forecloses later owner emails.** Once `info@` is on `contacts.email`, every person path is closed: enqueue `wantProfile = !email` (`enqueue-enrichment.ts:63`), `dropAlreadyDone` (**master** `:2605-2651`), `writeEmail` `.is("email", null)` (`:2545`), the Findymail hit via the same `writeEmail`. A future "upgrade to personal" needs an explicit overwrite rule: `.or("email.is.null,enrichment_data->enrichment->email->>kind.eq.company_generic")` plus the unique-index handling. Worth deciding before the opt-in is used at scale.
3. **Two owners, one inbox.** By design only one contact per firm gets the inbox (23505 -> `skipped`); the sibling keeps `company_email` only. Fine, but the picker should not count both as "has email".

## 6. Cost accounting

**In `enrichment_runs.cost_usd` today (master):** Apify batches at harvest from `usageTotalUsd`, else `items x estimatePerItem` (**master** `route.ts:203-210, 405-408, 588-591`), failed/stuck runs (`recordBadRunCost`, `:220`), completion reconcile (`reconcileRunCost`, `:2764`); pattern_mv `credits x 0.0037` + Findymail `$0.049/hit` (`:1094-1098`); verify credits (`:1823`); discovery **Perplexity tokens only** (`:1297`; `perplexity/client.ts:93` uses `calculateCost`; `pricing.ts:56-59` admits it); naming: Haiku 4.5 tokens + Haiku 5.5 tokens + `$0.01` web-search fee (**master** `layer2.ts:105-110`, `decision-maker/pricing.ts:14`).

**Not in it:** Perplexity's per-request fee (ledger: **$11.58 unrecorded** since 10-11, ~$4.51 before); sourcing (`linkedin_searches.cost_usd`, `maps_searches.cost_usd`); Scrap.io credits (prepaid; the skill writes `cost_usd: 0` and keeps credits in `query.scrapio.credits`, `source-import.mts:83, 102`); pre-send-gate MV credits (`verify-contact.ts`, attributed to no run or campaign); MV's real tier price (`pricing.ts:21-27` assumes the $37/10K bundle; memory says tiers differ ~8x); the site-scraper's external unblocker key; Apify's monthly plan floor. DNS is free.

**Structural gaps:**
1. **The reconcile floor drops non-Apify spend.** `cost_usd = max(accrued, sum of Apify final usage)` (**master** `:2818-2821`): whenever the Apify sum exceeds the accrual, the MV, Findymail and LLM shares are overwritten.
2. **Per-item `cost_usd` is a per-phase overwrite** (section 3), so per-provider totals cannot be rebuilt from items, and skips (`:875`, `dropAlreadyDone`) leave stale values.
3. **No per-provider or per-phase split**: profiles, domains, scrape and activity are different actors but one "Apify" number; the profile email lookup is charged per profile with or without an email (`pricing.ts:5`, mode label `profile-harvestapi.ts:5`), so its effective price (**$20.08 / 626 found ~ $0.032 per profile email, ~$0.058 per MV-ok one**, ledger + probe) is invisible.

**Being fixed in worktree `modest-curie` (uncommitted, not reviewed for correctness here):** migration `00138` adds `enrichment_runs.cost_breakdown` (apify / millionverifier / findymail / perplexity / anthropic); `addRunCost` writes total + share in one statement at every accrual site; `reconcileApifyCost` floors only the Apify share (fixes gap 1); `perplexityCallCost` adds the $0.005 request fee inside `callPerplexity`; `scripts/backfill-perplexity-fee.ts` replays past runs' call counts from item notes (`perplexity-calls.ts`). **Still needed after that:** a per-phase Apify split (derivable from the item run-id columns), per-item per-phase cost columns or an `enrichment_cost_events` ledger (run, item, provider, units, unit price, usd), the MV price basis as an org setting, and a "cost per sendable owner email, by provider" line in the run banner / client ledger.
